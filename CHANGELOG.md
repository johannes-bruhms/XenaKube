### Fixed (D66 — slide segment dur cap restores wild-gliss visual amplitude)
- User report 2026-04-30 (post-D65, working but observation): "the drawn 'amplitude' of the gliss 'wave' is reduced due to like some kind of data smoothing". Wild gliss with rapid up-down zigzags shows the visual oscillating with much smaller pitch swings than what the user audibly hears.
- **Root cause**: `_glissChainDur` (rolling-score) and `predictGlissDuration` (triangle) compute slide segment duration as `interval × per-semi` (e.g., 28 semi C5 = 1400 ms). With `MIN_GLISS_SPACING_MS = 200 ms` event spacing, each segment walks only `200/1400 = 14 %` of its arc (eased to ~6 %) before the next event override. For a 47↔75 wild-gliss zigzag, the visual amplitude collapses to ~1.6 semis from 28 — exactly the "data smoothing" feel the user described. SWAM's Mono Poly Release portamento meanwhile engages cleanly enough at 200 ms spacing to reach full target swings audibly. Both line and chain models had this collapse identically, so `assertGlissSync` didn't fire — they were agreeing on under-amplitude.
- **Fix**: new `GLISS_SLIDE_MAX_DUR_MS = 195` constant in `public/js/constants.js`. Both `_glissChainDur` and `predictGlissDuration` clamp slide duration at this value. 195 ms matches the bridge's `MIN_GLISS_SPACING_MS - BEND_DUR_MARGIN_MS = 195 ms` cap (already used for bend segment dur via D60.2 / D63.2), so a slide segment always completes before the next event boundary. Visual amplitude restored to full pitch swing the user perceives audibly.
- For typical slides where `interval × per-semi ≤ 195 ms` (~3 semis at C5, ~2 semis at C6), no behavioural change.
- For the LAST event of a phrase (no follow-up override): visual reaches target by 195 ms while SWAM's audio may still be sliding. Brief over-shoot in visual; release ramp covers it within ~120 ms. Acceptable trade.
- `assertGlissSync` continues to hold to floating-point precision — both models clamp identically. CLAUDE.md Visual Invariants row 3 ("Gliss-line trajectory equals drawn-note trajectory") gets `GLISS_SLIDE_MAX_DUR_MS` mentioned alongside the per-complex portamento times. tsc clean, 122/122 tests pass.

### Fixed (D65 — chain bend p0 inheritance unifies with line model)
- User report 2026-04-30 (post-D64, working state): `GLISS SYNC FAIL` still firing during normal wild-gliss play with ~4-semi drift, but audio + visuals look/sound fine. Forensic log showed nodes `[47*@765754, 56@765901, 72@766102]` and segSpan `[765754+0: 47→47] [765901+450: 47→56] [766102+195: 56→72]` — at nowMs=766153 (51 ms past bend start), chain pitch was 58.65 (17% along 56→72) while line pitch was 54.30 (17% along 50.79→72). Both correct under their own model, but the models disagreed.
- **Root cause**: `_buildGlissSegments` for bend nodes used the bend's stated `fromPitch` from the bridge OSC echo as `p0`. That's the LOGICAL source noteOn pitch. The line model uses `_displayedPitch(line, t_bend)` for its retarget — the AUDIBLE pitch at bend-start. When the prior segment (e.g., a 9-semi C5 portamento at 50 ms/semi = 450 ms) overlaps with the next event (`MIN_GLISS_SPACING_MS = 200 ms`), the prior portamento is only ~45% complete when the bend fires — audible-at-bend-start ≈ 50.79, stated fromPitch = 56. The 5-semi gap propagated through the bend's eased interpolation, producing the user-observed drift.
- **Fix**: `_buildGlissSegments` now sets `p0 = _glissPitchAt(n.onsetMs, segs)` for all non-first-node bends — the same `_glissPitchAt`-inheritance rule already used for noteon segments. Both line and chain now derive bend p0 from the prior segment's audible pitch at bend-start. With identical easing function, identical per-complex portamento times, and identical p0-inheritance rule, the two models agree to floating-point precision. `assertGlissSync` returns to its design purpose: catching ARCHITECTURAL drift (missed events, wrong segment, stale state) rather than legitimate model differences during overlapping portamento+bend.
- First-node bends (rare — chain starting mid-bend) still use stated `n.p0` since there's no prior segment to inherit from. CLAUDE.md Visual Invariants row 3 ("Gliss-line trajectory equals drawn-note trajectory") updated with D65 sub-invariant and the rationale. tsc clean, 122/122 tests pass.
- **On the unrelated `(index):1 Uncaught (in promise) Error: Corruption: not an sstable (bad magic number)`** — this is a Chrome IndexedDB / LevelDB internal error from the browser profile or a browser extension, not from XenaKube (the dashboard uses only localStorage). It's persistent in the user's profile but harmless to the application. To silence: clear site data for `localhost:3000` in DevTools → Application → Storage, or test in Incognito.

### Fixed (D64 — bridge↔preset pitchbend range alignment + smoother ramp)
- User report 2026-04-30 (still feeling leaps even after D63): "i'll try reduce pb range to 24 for both up and down in the vst menu. also, i think couple of times i forgot to save the swam preset so that it reverted back to 2 instead of the assumed 48". This is the silent-killer surface: MIDI pitchbend is a 14-bit wheel position with NO semitone information; SWAM does the conversion using its preset's Pitchbend Range setting. If the bridge's `PITCHBEND_RANGE_SEMI` and SWAM's preset disagree, the bridge sends value14 expecting one scale and SWAM applies another — audible bend silently differs from intended bend. With a 12× factor (preset reverted to ±2 default vs bridge at ±48), bends are 1/12 strength — visual shows the slide, audio plays a tiny waver, then `noteOff(source) + noteOn(target)` at end of bend fires the discrete jump → exactly the "leaping" perception even though the bridge is bending correctly.
- **D64.1 — `PITCHBEND_RANGE_SEMI` lowered to 24** to match the user's incoming preset change. The bridge dispatches `bendStep` for cross-string intervals up to ±24 semis; intervals beyond fall through to `leapStep` with the existing `BEND CLIP` log. Cross-string intervals > 24 will leap visibly (chain breaks) — fewer wide bends than at ±48, but cleaner SWAM response on what does bend. Tunable: bump back to 48 (or anywhere) in one constant if the SWAM preset is set differently.
- **D64.2 — startup log of bridge pitchbend range** in `bang()`. Every Max reload prints `=== BRIDGE PITCHBEND_RANGE_SEMI = ±N — verify this matches SWAM preset's Pitchbend Range ===` to `[print xk_swam]`. Cross-check against SWAM's preset every time. The mismatch surface won't bite us silently again; it'll be visibly mismatched in the log next to whatever you set in the preset.
- **D64.3 — `rampPitchbend` tick 15 ms → 5 ms** for finer ramp resolution. At ±24 with a 24-semi bend over 195 ms, 15 ms ticks step at 1.85 semis/tick (potentially audible as stepping); 5 ms ticks step at 0.62 semis/tick (smoothly continuous). 3× more MIDI events per bend (~40 vs ~13 per 195 ms ramp), but SWAM handles 200 Hz pitchbend with no problem. CC ramps stay at 15 ms (CC modulators don't need fast updates).
- The user's question about "udpsend loop from Max" addressed: visual already leads audio because vst~ buffers MIDI into the next audio cycle (5–20 ms) while udpsend fires the UDP packet within the same JS tick. Reordering the two `outlet()` calls in `noteOn` / `emitPitchbend` would change relative timing by microseconds, far below the audio buffer latency. The ordering isn't the cause of perceived leaping.
- tsc clean, 122/122 tests pass.

### Fixed (D63 — eliminate stationary tails in wild gliss; revert D62.2 cap)
- User report 2026-04-30 (third pass on temp1.png with sharper observation): "in the red circles we have STILL NOTES (which should NEVER happen in wild gliss, notes should ALWAYS be pitch bending at ALL TIMES)" + "between the red circles we have CONNECTED LINES which SHOULD NOT have been connected, since they SOUNDED AS LEAPS" + "whatever you just did, reduced the amount of activity in the wild gliss, which is NOT what i asked for". Two related real bugs and one wrong-direction fix:
- **D63.1 — revert D62.2 `BEND_MAX_SEMI = 12` cap.** D62.2 converted cross-string bends with intervals > 12 semis into leaps. Wild gliss with its 36–89 register and ≥ 8-semi `MIN_LEAP` produces many cross-string events at 12–48 semi intervals — D62.2 turned those into chain-breaks (leaps), reducing visible activity in exactly the way the user objected to. Reverted: `glissStep` dispatch uses `PITCHBEND_RANGE_SEMI = 48` (matching the SWAM preset) directly. Wild gliss extreme intervals bend rather than leap. The constant `BEND_MAX_SEMI` is removed.
- **D63.2 — tighten `BEND_DUR_MARGIN_MS` from 50 → 5 ms (eliminates stationary tails).** D60 capped `_bendDur` at `MIN_GLISS_SPACING_MS - 50 ms = 150 ms` so each bend completed 50 ms before the next event dispatched (race-safe). But that 50 ms became a STATIONARY HORIZONTAL TAIL between bend's atomic transition (noteOff source + noteOn target at end of ramp) and the next event. With C5's wide register (36–89), bend targets often clamped to `ROLL_MAX_MIDI = 84` or hit `ROLL_MIN_MIDI = 36` at the visible-axis extremes — those 50 ms tails rendered as visible horizontal lines at the top/bottom edges of the rolling-score, exactly the "still notes" the user circled. New margin: 5 ms. Bend ramp now fills the inter-event time; the residual 5 ms gap (~2 px on screen) is sub-perceptible.
- **D63.3 — race-safe `completeBend` on `glissStep` entry.** With the 5 ms margin, scheduling jitter could reverse the firing order: next event's `glissStep` dispatches BEFORE the bend's scheduled atomic-transition Task fires. Without protection, the in-flight bend's pitchbend offset would leak into the new event's `noteOn` audibly. Added `inst.bendPending` (params for the deferred transition) + `inst.bendPendingTask` (the scheduled Task) instance state. New `completeBend(inst)` helper: idempotent, fires bend reset + noteOff source + noteOn target in the original D59-mandated order, cancels the scheduled task. `glissStep` calls `completeBend(inst)` at entry so any pending transition is force-completed inline before dispatching. `cancelPhrase` and `bang` clear `bendPending` and cancel the task so a stolen mid-bend voice doesn't re-fire the transition after `allNotesOff` cleared state.
- The "connected lines that should be leaps" complaint was about bends at extreme intervals AUDIBLY feeling like leaps (SWAM's pitch-wheel response at ±30+ semis is fast enough to "thwip"). Visually those are correctly bends (not leaps), and after D63.2 the chain renders them as continuous slopes with no stationary tails. If the audible "thwip-feel" still bothers you, the lever is `_bendDur`'s per-complex `perSemi` table (currently 50 ms/semi for C5) — slowing it makes audible slides feel more gradual, but they'd reach further beyond `MIN_GLISS_SPACING_MS` and require a wider margin.
- tsc clean, 122/122 tests pass.

### Fixed (D62 — bend-grace cross-phrase chaining + bend interval cap)
- User report 2026-04-30 with temp1.png: wild gliss visual still bugged across multiple turns of fixes. Reading the image showed two real bugs underneath a fundamental "wild gliss is too wide" architectural concern.
- **D62.1 — bend chain-grace consumed exactly once.** The `bendChainUntilMs` / `bendChainTargetPitch` / `bendUntilMs` maps were SET on bendstep arrival but only naturally expired (after dur + 100 ms tail). Within that window, MULTIPLE later noteOns could match the ±1 pitch tolerance and all be tagged chainStart=false. If a second phrase's anchor noteon happened to land within ±1 of the first phrase's last bend target during the grace window, the new phrase chained onto the old one — visually presenting as one giant accidentally-merged chain. **Fix**: when the bend-grace override fires for one noteOn, the entry is `delete()`d immediately. One bend grants exactly one continuation; subsequent noteons compute chainStart from active state alone. Triangle's bendUntilMs is also cleared when D61's `chainStart=true` splices the line, defense-in-depth for the case where leap-after-bend coincides with bend-grace expiry.
- **D62.2 — `BEND_MAX_SEMI = 12` cap, independent of `PITCHBEND_RANGE_SEMI`.** A cellist doesn't slide more than ~12 semis on a single string; SWAM's physical model on a single string responds well to ±12 pitchbend but produces audio that doesn't match the visual slope at extreme bends (±20+, especially ±48). The user's ±48 SWAM preset configures the WIRE to accept that range, but the BRIDGE chooses how much of it to use. **Fix**: new `BEND_MAX_SEMI` constant (default 12) gates `bendStep` dispatch in `glissStep`. Cross-string intervals ≤ 12 semis bend (clean SWAM response, audible continuous slide). Cross-string intervals > 12 semis fall through to `leapStep` with the existing `BEND CLIP` log — clean discrete jump that audibly AND visually reads as a leap. The user's SWAM preset stays at ±48; bumping `BEND_MAX_SEMI` to 24 or 48 in one constant brings back wider bends if desired. Tunable knob, single source of truth.
- **Architectural note**: wild gliss with C5 register 36–89 (53 semis) and 12+ events at 200 ms spacing is fundamentally chaotic. We've shipped 9 D-numbered fixes around this surface in 2026-04-30 alone (D54/D55/D56/D57/D58/D59/D60/D61/D62). Each addressed a real bug but the seams kept tearing because the gestural design itself produces extreme intervals at high event density. Next step proposed to the user: choose between (a) tame the register to 48–72 / 24-semi span, (b) constrain pickPitch to same-string only for C5, (c) accept the chaos as wild-gliss character and stop iterating. D62 ships clean either way — independent of the architectural decision.
- tsc clean, 122/122 tests pass.

### Fixed (D61 — triangle line slid across leaps that fired during bend-grace)
- User report 2026-04-30 (post-D60): "wild gliss sometimes has leaps (which is to be expected) however the drawn notes are always connected regardless of leap or gliss." Rolling-score chain WAS breaking correctly at leaps (gap > GLISS_GAP_MS or chainStart=true triggers `buildGlissChains` to start a new chain). The visual continuity the user observed was on the WHITE TRIANGLE LINE: D59's bend-grace in `triangle.js noteOff` skipped the line splice when a noteoff arrived during the bend's grace window — needed for the bend's own atomic noteOff source / noteOn target gap so the line wouldn't flicker — but it also shielded the splice on a LEAP's source noteoff that happened to fire within the same window. Then the leap's target noteon arrived, `_findGlissLine` returned the still-alive line, and `noteOn` retargeted it from the displayed pitch to the leap's target via `predictGlissDuration` (interval × 50ms = up to 2000ms slide animation). The white line audibly "slid" across what was actually a discrete jump.
  - **Fix**: `triangle.noteOn` now accepts a `chainStart` parameter computed by `rolling-score.noteOn` (same unified classifier the chain rendering uses). For gliss complexes, `chainStart=true` splices any preserved line and creates a fresh instant-snap entry — overriding bend-grace at the noteOn moment. `chainStart=false` retains the previous slide-retarget behaviour for true slides and bend continuations. main.js's `handleMidiEcho` calls `rollingScore.noteOn` first to capture `chainStart`, then passes it to `triangle.noteOn`. Both modules now break-or-continue together at every noteon.
  - **Why bend-grace at noteOff still matters**: the bend's atomic transition fires noteOff(source) then noteOn(target) within sub-1ms; the dashboard sees them as two WS messages. Without bend-grace at noteOff, the line would briefly splice between those two messages and then re-create — visible flicker. The grace covers that gap. The leap case differs because the leap's source noteoff happens 50 ms BEFORE the leap's target noteon, and the next event's chainStart=true is the unambiguous "this is a fresh phrase start" signal that overrides the grace.
  - tsc clean, 122/122 tests pass.

### Fixed (D60 — wild gliss state corruption from D59)
- User report 2026-04-30: "wild gliss bugging the fuck out … drawing future notes, drawing multiple notes, drawing impossible gliss, doesn't sound correlated, white lines don't track properly." Investigation found three independent root causes in the D59 implementation, all critical. The user's question about whether `PITCHBEND_RANGE_SEMI = 48` was responsible was correct that it amplified the symptoms but it wasn't the cause — the bugs would manifest at any range, just less audibly at smaller ranges.
- **D60.1 — `bendStep` `humanPitch` double-jitter mismatch (worst bug).** `humanPitch` is NOT the small ±0.05 jitter I assumed when designing D59 — it has a 10% chance of shifting by ±1 *whole semitone*. The original `bendStep` did `var hpSource = humanPitch(sourcePitch)` to compute its end-of-bend `noteOff(hpSource)` and `inst.activeNotes.indexOf(hpSource)`. But `inst.activeNotes` was populated by an EARLIER, INDEPENDENT `humanPitch` call (from the source's `noteOn`); the two random rolls disagree ~10% of the time. Result: `noteOff(50)` for a held `noteOn(51)`. SWAM never released the real note. `inst.activeNotes.indexOf(50) === -1`, so the splice never removed the stale entry, queues piled up, and every subsequent `legatoNoteOverlap`'s `oldNotes` walk noteOff'd random already-finished notes. State corruption: stale notes ringing forever, audio decoupled from intent, dashboard showing notes the audio doesn't match. **Fix**: `bendStep` finds the actual held source via `Math.round`-tolerant match on `inst.activeNotes`, uses that for the end-of-bend `noteOff` AND the splice. OSC echo emits INTEGER pitches (matches the dashboard's `| 0` parse and chain-grace match). Single `humanPitch` call for target only. Defensive `BEND FAIL` log + leapStep fallback if `inst.activeNotes` doesn't contain a matching entry.
- **D60.2 — bend duration overran `MIN_GLISS_SPACING_MS`.** `_bendDur` for C5 wild gliss is 50 ms/semi. An 8-semi cross-string event = 400 ms bend. But events space at `MIN_GLISS_SPACING_MS = 200 ms`. The next event dispatched while the previous bend's pitchbend ramp was still running AND its scheduled `noteOff/noteOn` callback was still queued. Pitchbend ramp kept ramping, leaking offset (up to ±48 semis at full range) into the new event's `legatoNoteOverlap`'s `noteOn` audibly. The previous bend's `noteOff/noteOn` then fired AFTER the new event's dispatch, double-noteOn'ing the target and accumulating notes in `inst.activeNotes`. Compounded by D60.1's mismatched indexOf: every subsequent `noteOff` missed AND added a new entry. **Fix**: `_bendDur` clamps at `MIN_GLISS_SPACING_MS - BEND_DUR_MARGIN_MS = 150 ms` so a bend always completes ≥ 50 ms before the next event dispatches. C5 8-semi cross-string slide now bends in 150 ms instead of 400 ms — slightly snappier than the per-complex portamento rate would imply, but unambiguously a slide. C6/C7 typical intervals (1–3 semis) already fit within the cap; their bends are unchanged in shape.
- **D60.3 — dashboard rendered bend's future as a horizontal line.** For an in-flight bend (`bs.t0 + bs.dur > nowMs`), `buildGlissChains` was computing `x1 = timeToX(bs.t0 + bs.dur, nowMs, w)` which returned x > rightEdge. The chain's sampled Path2D then drew past the "now" line, with `_glissPitchAt(t > t0+dur, segs)` clamping to `p1` — visually, the bend's destination pitch as a horizontal line ahead of current time. **Fix**: `buildGlissChains` clamps the bend segment's visual `x1` at `rightEdge` while in flight. Segment math (`p0`/`dur`/`t0` for `_glissPitchAt`) stays unchanged; only the visual endpoint clamps. Same pattern as active midi notes' `x1 = rightEdge`.
- **D60.4 — chain-grace pitch tolerance.** Post-bend `noteOn(target)` echoes its pitch through `humanPitch`, which has the 10% ±1 semi shift. The dashboard's chain-grace override compared `expectedPitch === data.pitch` exactly, missing the match ~10% of the time and producing a spurious chain break at the target. **Fix**: chain-grace pitch match is ±1 semi tolerant (`Math.abs(expectedPitch - data.pitch) <= 1`).
- **Verification**: tsc clean, 122/122 tests pass. After Max v8 reload + dashboard reload, the wild gliss phrases that previously rang stale notes and drew impossible chains should now bend cleanly within their phrase-spacing budget. `BEND FAIL` log fires loudly if `bendStep` is ever asked to bend a pitch that isn't in `inst.activeNotes` (defensive — should never happen post-fix since `glissStep` is the only caller and it's invoked after a confirmed `noteOn`).

### Added (D59 cross-string slides via pitchbend)
- **D59 — `bendStep` cross-string slides via pitchbend wheel.** SWAM Cello's portamento engine can't slide across physical strings (D46) — and that's been the cause of every "expected slide, played as leap" report. D58 (per-complex `MAX_LEAPS_BY_COMPLEX`) constrained gliss targets to same-string for C6/C7 as a same-day patch; D59 is the durable answer. The held source note's pitch is bent via MIDI pitchbend wheel from source to target over the slide duration; SWAM's physical model produces a continuous audible curve regardless of which string the held note is logically on. At the bend's end, the bridge atomically resets bend, noteOffs source, noteOns target — leaving a clean MIDI state for subsequent events.
  - **Bridge changes** (`max/xk_swam.js`):
    - `PITCHBEND_RANGE_SEMI = 48` constant matches the SWAM preset's Master Tuning → Pitchbend Range setting (user configured ±48 on 2026-04-30, SWAM's max). Paired tunable; document.
    - `inst.pitchbend` / `inst.pitchbendRampTasks` instance state, reset in `cancelPhrase` (steal-safe) and `bang` (panic-safe). A stolen mid-bend voice would otherwise leak the bend offset into the next voice's first noteOn, drifting the new phrase off pitch.
    - `emitPitchbend(inst, value14)` — encodes 14-bit MIDI pitchbend (status `0xE0 + ch`, LSB | MSB << 7) and emits via `emitMidi`.
    - `rampPitchbend(inst, target, durMs)` — slew limiter paralleling `rampCC`, 15 ms tick.
    - `cancelPitchbendRamp(inst)` — cancels in-flight ramp tasks.
    - `bendStep(inst, sourcePitch, targetPitch, glissVel, accent, complex)` — full slide function. Computes target bend value, emits `/xk/midi/bendstep` OSC echo at start (single event per bend; dashboard interpolates), ramps pitchbend, schedules atomic ramp-end transition (`bend=0 + noteOff source + noteOn target` in that exact order — bend reset BEFORE noteOn target so the new note's physical-model attack transient plays at the correct pitch).
    - `glissStep` three-way dispatch:
      - same-string → `glissNote` (existing portamento overlap path).
      - cross-string + interval ≤ `PITCHBEND_RANGE_SEMI` → `bendStep`.
      - cross-string + interval > range → `leapStep` (with `BEND CLIP` log; rare since cello range is 53 semis max and most slides ≤ 30).
    - `glissBendCount` counter on inst, reset alongside slide/leap counters in `handleVoice`.
    - D42 invariant updated: `slides + bends + leaps < 1` triggers `GLISS FAIL`. Per-phrase log includes `bends=B`.
  - **OSC schema** (`src/osc-schema.ts`): `OSC.MIDI_BENDSTEP = '/xk/midi/bendstep'` with args `(voice, fromPitch, toPitch, durMs, complex)`. `npm run gen:max` regenerated `max/gen_includes.js`.
  - **Relay** (`relay.js`): forwards `/xk/midi/bendstep` as WS `midi_echo` with `kind: 'bendstep'`.
  - **Dashboard** (`public/js/`):
    - `main.js` `handleMidiEcho` dispatches `kind === 'bendstep'` to `rollingScore.bendStep` and `triangle.bendStep`.
    - `triangle.js` `bendStep(data)` — retargets existing white line (or creates fresh one) from `fromPitch` to `toPitch` over `durMs`; sets per-(voice, complex) `bendUntilMs` so the bridge's incoming `noteOff(source)` doesn't splice the line during the brief gap before `noteOn(target)`.
    - `rolling-score.js` `bendStep(data)` — records the bend as a first-class chain segment (synthesised event with `isBend=true`, explicit `p0`/`bendDur`); `_buildGlissSegments` honours the bend's authoritative start pitch and duration instead of recomputing via `_glissPitchAt`. Sets `bendChainUntilMs` + `bendChainTargetPitch` so the target noteon's `chainStart` is overridden to false (continuation), keeping the chain unbroken visually.
  - **Visual continuity**: the chain renders source as a flat segment, the bend as a smooth slant, and target as a continuation flat — one continuous Path2D stroke. Matches the audible curve to within Phase 1's `assertGlissSync` ±1 px tolerance.
  - **CLAUDE.md** Bridge Invariants table: new "Cross-string slide via pitchbend" row; existing D48 row updated to note that D59 makes the per-complex leap counter effectively inert (preserved as belt-and-suspenders fallback).
  - **`docs/osc-reference.md`** documents the new address.
  - **Verification**: tsc clean, 122/122 tests pass. Implementation matches the design doc in `docs/research_notes.md` § Cross-String Pitchbend Slides (D59 — design, 2026-04-30) — the design's atomic-transition ordering, paired-tunable constant, and bend-grace dashboard logic all shipped as designed.

### Fixed (D58 per-complex leap tolerance)
- **D58 — `MAX_LEAPS_BY_COMPLEX` per-complex leap tolerance.** User report 2026-04-30: "top half ones that start high and drop down. those played as two regular notes with leaps, meanwhile the lower half (start low and gliss up) seemed to work fine, even the last one that gliss back down." Root cause: D46 string-crossing geometry. `CELLO_STRINGS` encodes practical slide-comfortable ranges (C: 36–55 / G: 43–62 / D: 50–69 / A: 57–89). Pitches above 69 sit on the A string only — they can slide to anything ≥57 but not below. The unified `MAX_CONSECUTIVE_LEAPS = 1` allowed 50/50 slide-leap alternation on high-anchored phrases that descended past 57 (A-string lower bound), and short C6/C7 phrases never accumulated a counter so their cross-string drifts always leaped on the first event. The asymmetry the user described isn't direction-dependent — it's *which strings the source and target sit on*. Lower-half phrases stay in the C/G/D overlap zone (36–69) where almost every adjacent pair shares a string.
  - **Fix**: per-complex tolerance via `MAX_LEAPS_BY_COMPLEX = { 5: 1, 6: 0, 7: 0 }` and `maxLeapsFor(complexType)` helper. C5 keeps `maxLeaps = 1` (wild punch character preserved; existing `phraseC5` anchor seed unchanged). C6/C7 drop to 0 so every cross-string outcome is nudged to same-string. Counter starts at 0 (handleVoice default) so the gate `0 >= 0` is always true on cross-string for those complexes — no anchor seed needed.
  - **Telemetry**: `glissStep`'s nudge gate and `scheduleRelease`'s GLISS RUN FAIL check both read `maxLeapsFor(inst.activeComplex)`. The per-phrase `slides=S leaps=L` log line is unchanged. For C6/C7 (max=0), any leap means consecutiveLeapMax=1 > 0 → FAIL fires (would indicate a `nudgeToSameString` corner failure since post-D58 those complexes should never leap). For C5 (max=1), runs > 1 still fire FAIL.
  - **Why this isn't the long-term fix**: D58 forces same-string by avoiding cross-string targets entirely, which constrains pitch range per phrase. The proper answer is **pitchbend on a single held note** (D59 — design in `docs/research_notes.md` § Cross-String Pitchbend Slides) — produces an audible pitch curve from any source to any target regardless of physical string. D58 is the same-day playable fix; D59 is the durable answer. Once D59 lands, all entries in `MAX_LEAPS_BY_COMPLEX` can return to 0 (or higher if the user prefers occasional explicit leaps as a deliberate gesture).
  - CLAUDE.md Bridge Invariants D48 row updated.

### Fixed (D56 GLISS SYNC FAIL, D57 pizz dynamics)
- **D56 — `chainStart` preservation across note finalisation.** User report 2026-04-30: `GLISS SYNC FAIL voice=1 complex=5 line=490.26px chain=651.29px drift=161.03px linePitch=61.00 chainPitch=52.00`. The Phase 1 `assertGlissSync` invariant correctly fired on a real silent-failure surface that pre-dated the Phase 2 extraction.
