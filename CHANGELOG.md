### Fixed
- **SWAM bridge — full `phraseCX` audit against the Xenakis primary-source complex definitions.** Each of the 8 phrase generators was re-checked against `src/complexes.ts:14-23` (`COMPLEX_DESCRIPTIONS`) to verify the rendered gesture matches its label. C1 / C5 / C7 / C8 already matched ("ataxic cloud", "ataxic sliding", "ordered sliding flat", "quasi-unison atom"). C2, C3, C4, C6 drifted from their labels and are now corrected:
  - **C3 (OrderedCloudFlat)** — previously fired a single legato note with optional grace notes only at f+ (comment incorrectly said "sustained"). Now fires 3–5 legato rebows spaced across `dur`, each at the sieve centroid ±1 semitone (equal-probability 0 / ±1 jitter). "Ordered" = narrow pitch window, "flat" = non-directional. Release `dur * 1.3`. `max/xk_swam.js:1008-1023`.
  - **C2 (OrderedCloudAscDesc)** — the shared sieve walker (`state.sieveIdx` / `state.sieveDir`, also used by C6) would flip direction mid-phrase whenever it crossed a sieve boundary, so 2-note phrases (common at low intensity) couldn't establish direction and 4-note phrases could read `up-up-down-down`. New `commitSieveWalk(count)` helper pre-flips the walker + teleports to the opposite extreme when the current position can't fit `count` monotone reads, so each phrase walks in a single committed direction. Count floor raised from 2 to 3 (burst cap raised 5 → 6) so every cloud has room to read directionally. `max/xk_swam.js:990-1002`.
  - **C6 (OrderedSlidingAscDesc)** — same walker-flip problem as C2 (they share `pickPitch` case 2); now calls `commitSieveWalk(count)` before the gliss walk. `max/xk_swam.js:1082-1097`.
  - **C4 (IonizedAtom)** — rendered as a scattered harmonic wash across the full sieve with progressively-spaced attacks, which reads as a cloud but not as an "atom" (localized nucleus). Xenakis describes C4 as *"ionized atom: interferences with pizzicati"* — a compact pitch nucleus with irregular-timed attacks. Now 2–5 harmonic attacks clustered at the sieve centroid ±2 semi jitter, arriving at **random** delays across the spread (cf. C1's `rrand` timing = the "ionization"). SWAM bridge's harmonic rendering (D37) is unchanged; only pitch clustering + timing distribution moved. Note: the primary source says pizz, but the XenaKube bridge keeps harmonics per D37's cello-idiomatic mapping — the fix preserves that choice while restoring the "atom with ionized timing" structural character. `max/xk_swam.js:1029-1061`.
  - **New helper `commitSieveWalk(count)`** at `max/xk_swam.js:966-985` — small utility, pure mutation of `state.sieveIdx` / `state.sieveDir`, callable from any phrase that relies on the walker being monotone for its duration.

- **SWAM bridge — Tremolo Min Speed (CC 80) now follows a per-phrase stochastic envelope (D39, supersedes D38).** Performer report on D38: "extremely jittery and doesn't really do much." The 60 Hz `spinEMA×30 + ±12 breath` modulator reacted to every micro-spin and couldn't move the slider far enough to register as a musical gesture. Result: every tremolo phrase has a recognisable ascending / descending / steady character that spans the full audible rate range, instead of a continuous nervous wobble.

### Fixed
- **Snap thresholds now re-centre on the user's rest pose (`zero_gyro` mirror).** Symptom: after auto-zero or a Zero Gyro click, rotating the cube slightly in one direction would snap almost immediately while the opposite direction required much larger rotation — directional asymmetry in the 24-cell S4 snap partition. Root cause: `snapToNearest` runs in `src/quaternion.ts` against 24 fixed S4 quaternions in the raw sensor frame, while the dashboard's `gyroZeroInv` only re-framed the *visual* cube. The user's physical rest pose sat at an arbitrary point inside one cell, so cell-boundary distances were asymmetric from that point. Camera drag made the asymmetry visible because it aligned the user's "right/left" with the dashboard's world axes while the engine still lived in sensor axes. Fix: new `engineGyroZeroInv` on the relay, captured as `quatConj(kf.q)` whenever the dashboard sends a `zero_gyro` WS message (both auto-zero on first sample and the Zero Gyro button). Every `engine.onGyro(...)` call now receives `engineGyroZeroInv * kf.q`, so the engine sees identity at the zero moment and S4 cells become symmetric around the user's hold. Downstream consequence — `/xk/snap/*`, `/xk/gyro`, `/xk/expr/*`, and C_i-gyro mode all now live in user-calibrated frame, matching the dashboard's visual frame. Side-benefit: ghost cube (world-frame) and live cube (zeroed-frame) finally overlap when deviation≈0 (remap is a quaternion-homomorphism so both frames line up on a snap). `/gan/gyro` stays raw for TD consumers that want unfiltered sensor data.

- **Dashboard — `gyro_tick` is the sole writer of 60 Hz visual state; `state` / `gyro_state` stop touching `currentGyro`, `expr-dev`, and `computeLocalExpression`.** With SLERP in place, tick ships a smooth 120 ms-lagged quat while `state.gyro` kept writing fresh-but-choppy `kf.q` snapshots at BLE rate.
